Sesión 9 · Tuning de una MLP para producción eléctrica

Caso. Una planta de ciclo combinado opera a carga completa y necesita anticipar su producción eléctrica neta horaria a partir de temperatura, vacío de escape, presión y humedad.

Pregunta central. ¿Qué arquitectura y régimen de entrenamiento ofrecen el menor error fuera de muestra bajo un presupuesto explícito, y qué podemos decir —con prudencia— sobre las predicciones del modelo final?

Al terminar podremos responder:

  1. ¿La MLP supera referencias lineales y tabulares?
  2. ¿Qué configuraciones exploraron KerasTuner y Optuna y cuánto costaron?
  3. ¿El resultado se sostiene entre semillas?
  4. ¿En qué condiciones falla más?
  5. ¿Qué muestran PDP/ICE y SHAP sobre la función predictiva?

1. Contrato experimental antes de entrenar

  • El test se separa al inicio y permanece cerrado hasta elegir la configuración.
  • Los escaladores se ajustan exclusivamente con train durante el tuning.
  • Ambos tuners reciben el mismo espacio conceptual y presupuesto máximo.
  • EarlyStopping limita épocas dentro de cada trial; Optuna además puede podar trials.
  • La selección usa validación. MAE, RMSE y \(R^2\) de test se calculan una sola vez al final.

El entorno DL_TUNING_MODE controla el presupuesto: smoke, class o full.

2. Datos y significado

El conjunto Combined Cycle Power Plant contiene 9.568 promedios horarios recogidos entre 2006 y 2011 mientras la planta operaba a carga completa. Las variables son:

  • AT: temperatura ambiente (°C).
  • V: vacío de escape (cm Hg).
  • AP: presión ambiente (mbar).
  • RH: humedad relativa (%).
  • PE: producción eléctrica neta (MW).

La fuente no incluye fecha ni identificador temporal. Por ello solo podemos hacer una partición aleatoria y debemos declarar como limitación que no medimos generalización hacia años futuros.

4. Una fábrica común de modelos

KerasTuner y Optuna deben construir la misma familia. Cada configuración contiene:

  • n_layers: 1–3 capas ocultas;
  • units_i: 32, 64 o 128 unidades en cada capa activa;
  • dropout: 0, 0,1, 0,2 o 0,3;
  • batch_size: 32, 64 o 128;
  • learning_rate: \(10^{-4}\) a \(3\times10^{-3}\) en escala logarítmica.

La salida es lineal. Entrenamos sobre un target estandarizado, pero volvemos a MW para comunicar resultados.

def build_mlp(config, seed=SEED):
    tf.keras.backend.clear_session()
    tf.keras.utils.set_random_seed(seed)
    inputs = tf.keras.Input(shape=(len(FEATURES),), name="condiciones")
    x = inputs
    for i, units in enumerate(config["units"]):
        x = tf.keras.layers.Dense(
            units, activation="relu", kernel_initializer="he_normal", name=f"dense_{i+1}"
        )(x)
        if config["dropout"] > 0:
            x = tf.keras.layers.Dropout(config["dropout"], seed=seed + i, name=f"dropout_{i+1}")(x)
    outputs = tf.keras.layers.Dense(1, name="pe_estandarizada")(x)
    model = tf.keras.Model(inputs, outputs)
    model.compile(
        optimizer=tf.keras.optimizers.Adam(config["learning_rate"]),
        loss="mse",
        metrics=["mae"],
    )
    return model

¿Por qué no GridSearch exhaustivo?

Con 1–3 capas y tres anchos posibles hay \(3 + 3^2 + 3^3 = 39\) arquitecturas. Al multiplicar por cuatro tasas de dropout, tres batches y apenas cuatro tasas de aprendizaje discretizadas aparecen 1.872 configuraciones. Early stopping reduce épocas, pero no elimina esta explosión de trials.

5. KerasTuner: construcción y entrenamiento como hiperparámetros

HyperModel.build() controla la arquitectura y el optimizador. HyperModel.fit() recibe el modelo ya construido y permite elegir el batch sin perder los callbacks internos del tuner.

class PowerPlantHyperModel(kt.HyperModel):
    def build(self, hp):
        n_layers = hp.Int("n_layers", 1, 3)
        all_units = [hp.Choice(f"units_{i}", [32, 64, 128]) for i in range(3)]
        config = {
            "n_layers": n_layers,
            "units": all_units[:n_layers],
            "dropout": hp.Choice("dropout", [0.0, 0.1, 0.2, 0.3]),
            "batch_size": hp.Choice("batch_size", [32, 64, 128]),
            "learning_rate": hp.Float("learning_rate", 1e-4, 3e-3, sampling="log"),
        }
        return build_mlp(config)

    def fit(self, hp, model, *args, **kwargs):
        return model.fit(
            *args,
            batch_size=hp.get("batch_size"),
            **kwargs,
        )

6. Optuna: objetivo define-by-run y pruning

El callback reporta val_loss después de cada época. El MedianPruner puede abandonar una configuración cuando su trayectoria es poco competitiva frente a trials previos. Early stopping sigue activo: los mecanismos cumplen papeles distintos.

class OptunaPruningCallback(tf.keras.callbacks.Callback):
    def __init__(self, trial, monitor="val_loss"):
        super().__init__()
        self.trial = trial
        self.monitor = monitor

    def on_epoch_end(self, epoch, logs=None):
        value = (logs or {}).get(self.monitor)
        if value is None:
            return
        self.trial.report(float(value), step=epoch)
        if self.trial.should_prune():
            raise optuna.TrialPruned(f"Podado en época {epoch + 1}")

def optuna_objective(trial):
    config = {
        "n_layers": trial.suggest_int("n_layers", 1, 3),
        "units": [],
        "dropout": trial.suggest_categorical("dropout", [0.0, 0.1, 0.2, 0.3]),
        "batch_size": trial.suggest_categorical("batch_size", [32, 64, 128]),
        "learning_rate": trial.suggest_float("learning_rate", 1e-4, 3e-3, log=True),
    }
    config["units"] = [
        trial.suggest_categorical(f"units_{i}", [32, 64, 128])
        for i in range(config["n_layers"])
    ]
    model = build_mlp(config, seed=SEED + trial.number)
    started = time.perf_counter()
    try:
        history = model.fit(
            X_train_s, y_train_s,
            validation_data=(X_val_s, y_val_s),
            epochs=BUDGET["epochs"], batch_size=config["batch_size"],
            callbacks=[
                OptunaPruningCallback(trial),
                tf.keras.callbacks.EarlyStopping(
                    monitor="val_loss", patience=BUDGET["patience"], restore_best_weights=True
                ),
            ],
            verbose=0,
        )
        values = history.history["val_loss"]
        trial.set_user_attr("best_epoch", int(np.argmin(values) + 1))
        return float(np.min(values))
    finally:
        trial.set_user_attr("seconds", time.perf_counter() - started)

8. El mejor trial puede ser una inicialización afortunada

Reentrenamos el ganador de cada herramienta con tres semillas en modos class y full. En smoke usamos una sola repetición porque ese modo verifica integridad, no estabilidad. Elegimos por MAE medio de validación y conservamos la dispersión.

def validate_candidate(label, config, seed):
    model = build_mlp(config, seed=seed)
    started = time.perf_counter()
    history = model.fit(
        X_train_s, y_train_s,
        validation_data=(X_val_s, y_val_s),
        epochs=BUDGET["epochs"], batch_size=config["batch_size"],
        callbacks=[tf.keras.callbacks.EarlyStopping(
            monitor="val_loss", patience=BUDGET["patience"], restore_best_weights=True
        )],
        verbose=0,
    )
    pred = y_scaler.inverse_transform(model.predict(X_val_s, verbose=0)).ravel()
    return {
        "candidato": label,
        "semilla": seed,
        "MAE_MW": mean_absolute_error(y_val, pred),
        "RMSE_MW": mean_squared_error(y_val, pred) ** .5,
        "best_epoch": int(np.argmin(history.history["val_loss"]) + 1),
        "segundos": time.perf_counter() - started,
    }

robustness_rows = []
for label, config in candidate_configs.items():
    for offset in range(BUDGET["repeats"]):
        robustness_rows.append(validate_candidate(label, config, SEED + 100 + offset))

9. Reentrenamiento y única apertura del test

Fijamos la configuración con menor MAE medio y la mediana de sus mejores épocas. Después:

  1. reunimos train + validación;

11. PDP e ICE: interrogar la función predictiva

Para una grilla de temperatura o vacío sustituimos esa columna en todas las observaciones de test y promediamos las predicciones. Las líneas ICE conservan respuestas individuales.

Esto describe el modelo, no una intervención causal. Las combinaciones artificiales pueden salir de las regiones más frecuentes del conjunto.

def predict_mw(values):
    frame = pd.DataFrame(values, columns=FEATURES)
    scaled = x_scaler_dev.transform(frame).astype("float32")
    pred_s = final_model(scaled, training=False).numpy()
    return y_scaler_dev.inverse_transform(pred_s).ravel()

def pdp_ice(feature, n_grid=25, n_ice=25):
    grid = np.linspace(X_test[feature].quantile(.02), X_test[feature].quantile(.98), n_grid)
    ice_base = X_test.sample(min(n_ice, len(X_test)), random_state=SEED).copy()
    pdp_values, ice_values = [], []
    for value in grid:
        pd_frame = X_test.copy()
        pd_frame[feature] = value
        pdp_values.append(predict_mw(pd_frame).mean())
        ice_frame = ice_base.copy()
        ice_frame[feature] = value
        ice_values.append(predict_mw(ice_frame))
    return grid, np.asarray(pdp_values), np.asarray(ice_values).T

13. Dictamen para el responsable de la planta

Conclusión de esta ejecución (mode=class)

  1. Optuna encontró la mejor MLP bajo el presupuesto disponible. Su arquitectura 4 → 32 → 32 → 64 → 1, sin dropout, batch 64 y learning rate \(1,91\times10^{-4}\) alcanzó un MAE medio de validación de 3,169 MW, 7,1 % menor que el candidato de KerasTuner (3,412 MW). La variación entre tres semillas fue pequeña (SD = 0,020 MW), por lo que la diferencia no parece explicarse únicamente por una inicialización afortunada.

  2. El pruning redujo cómputo, pero no permite declarar que Optuna sea universalmente superior. Optuna completó 4 de 8 trials y podó 4; consumió 88,3 s, frente a 129,6 s de KerasTuner. El ahorro observado fue cercano al 32 %, pero se compararon TPE con pruning y búsqueda bayesiana sin pruning, no solamente dos implementaciones equivalentes.

  3. El tuning mejoró la red, no el ganador global. En test, la MLP afinada logró MAE = 3,115 MW, RMSE = 4,008 MW y \(R^2=0,942\). Mejoró 8,1 % el MAE de la MLP fija y 11,9 % el modelo lineal. Sin embargo, boosting obtuvo MAE = 2,359 MW, RMSE = 3,156 MW y \(R^2=0,964\): un MAE 24,3 % menor que la MLP afinada. Para estos datos tabulares, no hay evidencia para recomendar la red como modelo productivo principal.

  4. El error medio es relativamente estable, aunque persisten casos extremos. El MAE por cuartil de temperatura varió entre 2,823 y 3,346 MW y el sesgo medio permaneció cerca de cero. El segmento más difícil fue el de temperaturas más bajas, seguido por el más cálido; los boxplots también muestran errores aislados superiores a 10 MW que ameritan revisión individual.

  5. La función aprendida atribuye el mayor cambio a la temperatura. El PDP de AT desciende de aproximadamente 482 a 435 MW entre 6 y 32 °C; el de V disminuye de forma más moderada, alrededor de 460 a 449 MW. Las curvas ICE revelan heterogeneidad, especialmente para V, por lo que el promedio no representa igual a todas las observaciones. Son asociaciones del modelo, no efectos causales ni recomendaciones de operación.

  6. El SHAP local explica una predicción baja, pero también descubre un error relevante. Para el caso AT=34,14, V=74,34, AP=1000,19, RH=43,56, la predicción fue 425,61 MW frente a 434,23 MW observados: una subestimación de 8,62 MW. Respecto a la referencia de 455,18 MW, AT aportó −24,06 MW, V −5,68 MW, AP −2,95 MW y RH +3,12 MW. Esto explica la salida del modelo; no demuestra mecanismos físicos.

  7. La selección sigue censurada por el presupuesto. Las tres repeticiones del candidato de Optuna alcanzaron la época máxima 60, de modo que early stopping no confirmó convergencia. Debemos llamarlo mejor configuración encontrada con 8 trials y 60 épocas, no arquitectura óptima. Antes de cerrar el estudio convendría ampliar únicamente el presupuesto del candidato final y comprobar si su validación todavía mejora, manteniendo test cerrado.

Recomendación al responsable

Usar boosting como referencia operativa preferida por su menor error y menor complejidad de entrenamiento. Conservar la MLP afinada como experimento comparativo y como base para estudiar estabilidad e interpretabilidad. Ninguno de los resultados permite inferir causalidad ni desempeño futuro: el conjunto no incluye fechas para validación temporal y solo representa operación a carga completa.
